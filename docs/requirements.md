# Promptarium 初期要件・決定事項

**状態:** 実装開始（要件ヒアリング第5回を反映）
**根拠:** プロジェクト依頼文およびユーザー回答（質問1〜22）
**更新日:** 2026-08-26

## 1. 目的

Promptarium は、ComfyUI などで生成した画像を、画像ファイル内に残る生成情報と結び付けて、ローカルで検索・確認・再利用できるようにするアプリケーションである。

画像は単なるファイルではなく「画像 + 生成レシピ」として扱う。ただし、画像だけから復元できない情報を確定情報のように扱わない。

## 2. 確定したMVP方針

| 項目 | 決定 |
| --- | --- |
| 中心ユースケース | フォルダ登録 → 手動または差分スキャン → 一覧・詳細表示 → 検索 → 分類修正 → カテゴリ単位コピーまたはworkflow JSON出力 |
| 解析対象 | ComfyUI PNG。標準ノードと、今後収集する実利用の代表ワークフローを保証対象とする |
| 未知の構成 | 未知ノード・情報不足・破損があっても画像登録を継続し、部分解析または解析不能として理由を示す |
| 画像の管理 | 元画像を変更しない参照方式。Promptarium内へのコピー／取り込み方式はMVP対象外 |
| 利用環境 | 単一のWindows PCとローカルSSDを主対象とする。接続先が利用不能な場合は削除ではなくオフライン／所在不明として扱う |
| スキャン | 手動スキャンと差分スキャンをMVPの基準とする。常時監視はMVP必須ではない |
| 分類 | 元の正負プロンプト全文を不変の出典として保持し、少数カテゴリへの複数所属、未分類、ルール／辞書と手動修正を許可する |
| 性能設計規模 | ローカルSSD上の最大10,000枚程度を、初期の設計・検証規模とする。具体的な時間目標は未決定 |
| 実データ検証 | 匿名化した実PNGを用い、代表ワークフローの解析可否を検証する |
| メタデータなし画像 | 登録・検索を可能にし、必要に応じてユーザーが生成情報を手動入力・編集できる |
| 検索 | フリーワードと、モデル・LoRA・タグ・カテゴリの絞り込みをAND条件で組み合わせる |
| NSFW表示 | MVPでは、サムネイルのぼかし・非表示・保護モードを設けない。ローカル完結の制約は維持する |
| バックアップ | Promptarium固有のユーザー情報を手動でバックアップ・復元できることをMVP要件とする。自動世代管理は後回し |
| 再利用 | 元プロンプトまたはカテゴリ単位でのクリップボードコピーまでをMVPとする。複数画像から新規プロンプトを組み立てて保存するビルダーは対象外 |
| 改名・移動の再照合 | パス、ファイルサイズ、更新日時などで候補を絞り、必要時にバックグラウンドで完全ハッシュを計算することを許容する |
| ライブラリ画面 | サムネイルのグリッド表示を主表示とする |
| 登録フォルダ | MVPから複数のスキャンルートを登録できる |
| サブフォルダ | 各スキャンルートは標準でサブフォルダを再帰走査する |
| ユーザー評価 | お気に入り、未評価または1〜5星の評価、メモをMVPに含める |
| 初期並び順 | ファイル更新日時の新しい順 |
| 完全重複 | 内容が完全に同一の画像は1つの画像資産としてまとめ、複数の保存場所を表示する |

## 3. MVPに含める機能境界

### Must

- ユーザーが指定した複数フォルダ内のPNGを、元画像を変更せずに登録・再スキャンできる。
- 各スキャンルートは、既定でサブフォルダを再帰走査する。
- ComfyUI由来のメタデータを取得し、生のメタデータ、prompt JSON、workflow JSONが存在する場合は保持できる。
- メタデータがない画像も登録・検索でき、ユーザーは必要なプロンプトや生成情報を任意で入力・編集できる。
- ポジティブ／ネガティブプロンプト、モデル名、LoRA、VAE、Seed、Steps、CFG、Sampler、Scheduler、画像サイズについて、取得できた値と情報源を表示できる。
- 解析結果を「正常」「一部成功」「未知ノードを含む」「情報なし」「破損」「解析不能」など、確定度を誤解させない状態で示せる。
- サムネイルグリッドを中心とした画像ライブラリを提供する。大量件数でも画面外の項目を一括描画しない。
- フリーワードと、モデル・LoRA・タグ・カテゴリをAND条件で組み合わせた検索を提供する。
- 各画像に対して、お気に入り、星評価、メモを記録・編集できる。
- 画像一覧は、既定でファイル更新日時の新しい順に並べる。
- プロンプトを分類し、ユーザーが分類結果を修正できる。
- 元のプロンプト、生データ、自動解析、自動分類、ユーザー修正を区別して保持する。
- 元プロンプトまたはカテゴリ単位でクリップボードへコピーし、workflow JSONを出力できる。
- Promptarium固有のユーザー修正、分類、メモなどを手動でバックアップ・復元できる。
- 指定外フォルダを走査せず、画像・プロンプトを無断で外部送信しない。

### Should

- 登録ルート内での改名・移動を、パス、サイズ、更新日時で候補を絞り、必要時にはバックグラウンドの完全ハッシュ計算も用いてベストエフォートで再照合する。
- 内容が完全に一致する複数ファイルを、1つの画像資産と複数の保存場所として表示する。
- 未分類タグの確認と、分類ルールへの登録を支援する。

### Could（MVP後）

- 常時フォルダ監視、Promptarium管理領域への画像取り込み、NASでの性能保証。
- JPEG、WebP、AVIF、Stable Diffusion WebUI、Forgeへの対応。
- 本格的なプロンプトビルダー、AI／LLMによる分類や画像内容推定、類似画像検索。
- Civitai・ComfyUI API連携、複数PC同期、Web／モバイル表示、複数ユーザー。

## 4. データ保全・正確性の不変条件

1. 元画像は読み取り対象であり、Promptariumはユーザーの明示操作なしに画像の内容・名前・配置を変更しない。
2. 画像から取得した生のメタデータと元プロンプト文字列は、正規化・分類・編集結果とは別に保存する。
3. メタデータ抽出、ワークフロー解析、ユーザー入力、AI推定、情報源不明を同じ確度で表示しない。
4. 自動解析や自動分類の再実行は、ユーザーによる修正を消去しない。
5. 不明・破損・未知ノードを理由に、他の画像のスキャン処理を停止しない。
6. モデル名やLoRA名が画像内に記録されているだけでは、ローカルの実ファイルを一意に断定しない。
7. ユーザーが手動入力・編集した値には情報源を記録し、抽出された原本を上書きしない。

## 5. 解析・分類の初期方針

- ComfyUIの `prompt` JSON と `workflow` JSON は、存在すればいずれも原本として保持する。どちらを主解析経路にするか、両者の不整合をどう扱うかは技術スパイクで決める。
- 固定のノードIDや単純な表示名だけに依存しない。接続関係、入力値、出力への経路を基に解析する。
- 初期の分類は「キャラクター」「ポーズ／行動」「シチュエーション／環境」「スタイル／品質」「構図／カメラ」とする。将来の拡張余地は残すが、MVPでの独立カテゴリはこの5つに限定する。
- 1つのタグは複数カテゴリに属し得る。どのカテゴリにも属さないタグを明示的に扱う。
- 元のポジティブプロンプト全文は親カテゴリや残余カテゴリではなく、不変の原文・出典として扱う。
- 解析対象を決める際は、匿名化した実PNGを用いる。各フィクスチャには期待する抽出結果、対応するワークフロー種別、既知の未対応点を記録する。
- 実利用のワークフロー構成は未把握である。技術スパイクの出発点として、標準的なチェックポイント読込、正負のテキストエンコード、KSampler、VAEデコード、画像保存の経路と、任意のLoRA／VAE読込を対象にする。保証範囲は実PNGの棚卸し後に確定する。

## 6. MVPで保証しないこと

- すべてのComfyUIカスタムノード、あらゆるワークフロー、すべての画像形式の完全解析。
- 画像のみからの元プロンプト、Seed、モデル、LoRA、生成パラメータの完全復元。
- ファイル移動・改名・重複の完全自動追跡。
- NASや低速ストレージ上での、ローカルSSDと同等の性能または常時監視の保証。
- モデル／LoRA実体の完全なハッシュ照合、外部サービスとの自動照合。
- AI分類、外部API送信、画像内容の推定。
- NSFW画像に対するサムネイルのぼかし・非表示・アクセス保護。
- 複数画像の要素を組み合わせた新規プロンプトの保存、テンプレート、プリセット、重み・順序を編集する本格的なプロンプトビルダー。

## 7. 現時点で残る重要な未決定事項

- 実際に使用するComfyUIのモデル系統、代表ワークフロー、カスタムノード、およびテスト用サンプルの入手方針。
- 代表ワークフローの種類と、匿名化サンプルの具体的な提供方法。
- OR／NOT検索、数値範囲検索、保存検索、コピー・エクスポート形式。
- お気に入り・評価・メモを検索条件に含める範囲。
- 複数スキャンルートの個別の有効／無効設定。
- 改名・移動・重複を検出する精度と、手動での関連付け修正の必要性。
- バックアップの対象、保存先、エクスポート形式、移行手順。
- 永続化方式、GUI方式、技術スタック、具体的な性能目標値。

## 8. 次の検討順序

1. 実データに基づく解析対象・テストフィクスチャの範囲を決める。
2. 検索、再利用、プライバシー、バックアップの利用要件を決める。
3. 技術スパイクの成功条件を定義する。
4. その結果を基に、データ保存方式とGUI技術を比較する。
